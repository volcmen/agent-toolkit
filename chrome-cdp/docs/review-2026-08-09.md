# Chrome CDP implementation review

Reviewed through 2026-08-11 on branch `feat/chrome-cdp-spotlight-launcher`.

## Scope

The review traced the fixed configuration, classifier precedence, profile and lock filesystem boundaries, macOS process/listener inspection, CDP validation, launch orchestration, helper command contract, app assembly/signing, and atomic install/rollback flow.

## Resolved findings

- Duplicate Chrome arguments, wrong-profile precedence, endpoint failures, and stable actionable errors received direct classifier coverage.
- Profile and lock handling now validates identities with no-follow descriptors, exact modes including special bits, hard-link rejection, cooperative first-acquisition races, latched lock identity, crash release, and bounded waits.
- Process observation bounds kernel argument parsing, drains child output safely, handles protected processes, and uses the supported `proc_pidpath` buffer size.
- CDP observation rejects redirects, wrong response URLs, unsafe WebSocket hosts/ports, malformed target data, request failures, and timeouts; cancellation propagates.
- Launch orchestration stops at monotonic deadlines, releases its lease on every post-acquisition path, launches only from clean state, creates a blank page only when necessary, and activates the validated PID.
- Helper self-check validates the complete production configuration. Chrome bundle validation walks untrusted app components without following symlinks.
- App and helper are ad-hoc signed and strictly verified. The installer backs up and manifests the previous bundle, verifies sibling staging paths, uses native atomic swap, rolls back failed verification, and confirms LaunchServices handlers are unchanged.

## Verification approach

Changes were developed with focused failing regressions followed by the aggregate test runner. Review fixes were rechecked with Swift strict concurrency and warnings-as-errors. Final live validation was deliberately limited to the dedicated loopback endpoint and recorded without URLs, titles, credentials, or profile contents.

The remaining trust boundaries are macOS Launch Services resolving `Google Chrome` after path validation and the current user's ability to replace same-user files during execution. Unknown processes and unsafe paths fail closed.
